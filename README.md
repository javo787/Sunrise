# Sunrise CRM — автоматизация отдела продаж застройщика

Поток ~200 лидов в день: **Meta / Instagram Direct / WhatsApp / ручной ввод → ИИ-квалификация → «Shark Tank» в Telegram → Google Sheets → отчёты**.
Веб-интерфейса нет: менеджеры работают в Telegram и в таблице SUNRISE CRM.

Стек: Next.js 14 (только API Routes) · TypeScript · MongoDB · grammY · `@googleapis/sheets` · Gemini / OpenAI · node-cron · nodemailer.
Рассчитан на **один долгоживущий Node-процесс** (Render / VPS), не на serverless: склейка сообщений и фоновая обработка после ответа вебхука живут в памяти процесса.

## Как это работает

```
Meta leadgen ─┐                                   ┌─ карточка в группе (номер скрыт)
Instagram DM ─┼─► ИИ-бот ─► квалифицирован? ─►  ──┤      🦈 Забрать в работу
WhatsApp ─────┤   (цены из кода)   телефон+этаж+  │          │ атомарный захват в БД
Ручной ввод ──┘                    оплата         │          ▼
   (➕ в боте)                                      │   победителю — контакт в личку,
                                                   │   карточка → «✅ Забрал: Имя»,
                                                   │   строка → лист «Менеджер N»
                                                   └─ 15 минут без владельца → cron тегает менеджеров и руководителя
```

* **Дедупликация клиентов** — по нормализованному телефону, уникальный индекс в MongoDB; одновременные вебхуки не создают двух лидов.
* **Shark Tank** — переход `pending → claimed` выполняется одним `findOneAndUpdate` с условием `status: 'pending'`: при одновременных нажатиях выигрывает ровно один.
* **ИИ не считает цены.** Код подставляет в промпт готовую справку из `lib/domain/pricing.ts`; если модель «узнала» этаж позже, ответ перегенерируется с верными цифрами.
* **Лиды не теряются**: недоступен ИИ → лид создаётся с пометкой; недоступен Telegram → карточку досылает cron; недоступна таблица → запись повторяется до `SHEETS_SYNC_MAX_ATTEMPTS`; не получилась лид-форма Meta → повтор в течение 24 часов.
* Вебхуки Meta / Evolution / Telegram отвечают `200` сразу, повторы доставки отсекаются по id события.
* **Сообщения не теряются при перезапуске.** Каждое входящее сообщение клиента сначала пишется в БД (коллекция `inbox`), в памяти остаётся только склейка; если процесс перезапустился до обработки, cron через 3–8 минут добирает такие сообщения. Голосовые в этом случае восстанавливаются как текстовая пометка (само аудио в БД не хранится).
* **После передачи лида менеджеру** бот клиенту не отвечает, а новые сообщения клиента пересылаются закрепившему менеджеру в личку (пока лид не забран — в тред карточки в группе, без телефона).

## Запуск

**Пошаговая инструкция по бесплатному развёртыванию (Render + MongoDB Atlas + cron-job.org) — в [DEPLOY.md](DEPLOY.md).**

```bash
cp .env.example .env.local      # заполнить значения
npm install
npm run dev                     # или: npm run build && npm start
npm test                        # 279 тестов
```

1. **MongoDB** — `MONGODB_URI`, индексы создаются автоматически при первом обращении.
2. **Telegram**: создать бота в @BotFather, добавить в группу менеджеров, в группе отправить `/whoami` → `TELEGRAM_MANAGERS_CHAT_ID`; свой ID (`/whoami` в личке) → `TELEGRAM_ADMIN_IDS`.
   Зарегистрировать вебхук: `PUBLIC_BASE_URL=https://домен npm run setup:telegram`.
3. **Менеджеры**: каждый нажимает `/start` у бота в личке (иначе контакты не придут), руководитель подключает:
   `/addmanager 123456789 Менеджер 1 Алиса Каримова` (листы «Менеджер 1–3», один лист — один человек).
   Остальное: `/managers`, `/removemanager <id>`, `/report day|month`.
4. **WhatsApp (Evolution API)**: в инстансе включить вебхук на `https://домен/api/whatsapp-webhook?secret=<WHATSAPP_WEBHOOK_SECRET>`, событие `MESSAGES_UPSERT`.
5. **Meta**: приложение с продуктом Webhooks, подписка страницы на поле `leadgen` (объект *Page*) и на сообщения Instagram. Callback URL `https://домен/api/meta-webhook`, verify token = `META_VERIFY_TOKEN`. Токен страницы должен иметь `leads_retrieval`, `pages_show_list`, `pages_manage_metadata`, `instagram_manage_messages`.
6. **Google Sheets**: сервисный аккаунт → ключ JSON в `GOOGLE_SERVICE_ACCOUNT_JSON`, таблицу расшарить на e-mail аккаунта с правом «Редактор», ID таблицы → `SHEETS_SPREADSHEET_ID`.
   **Проверка таблицы перед запуском** (ничего не записывает):
   `curl -H "x-cron-secret: $CRON_SECRET" https://домен/api/cron/sheets-check` — покажет по каждому листу найденные колонки, заголовки, которые код не трогает (формулы), первую свободную строку, и значения справочников из кода, которых нет на листе `_Lists`.
7. **Деплой на Render**: `render.yaml` в корне настроен на бесплатный тариф; чтобы сервис не засыпал, внешний cron-job.org дёргает `/api/cron/publish-and-escalate` раз в минуту (см. DEPLOY.md). CI на GitHub Actions: типы → тесты → сборка.
8. **Cron** запускается сам (`instrumentation.ts`, часовой пояс `TIMEZONE`). Если нужен внешний планировщик: `ENABLE_INTERNAL_CRON=off` и вызовы `GET /api/cron/<job>` с заголовком `x-cron-secret`.

| Задача | Расписание | Что делает |
|---|---|---|
| `publish-and-escalate` | каждую минуту | досылает неопубликованные карточки; тегает по лидам старше 15 мин (один раз) |
| `retry-failed` | каждые 5 мин | повтор записи в таблицу, лид-форм Meta и сообщений клиентов, не обработанных при перезапуске |
| `report-daily` | 20:00 | дневной отчёт в Telegram и на Email |
| `report-monthly` | 28–31 числа 20:30 | месячный отчёт, уходит только в последний день месяца |

Отчёты идемпотентны (слот периода в БД): при нескольких инстансах уйдёт один.

## Таблица SUNRISE CRM

Запись идёт **точечно в ячейки входных колонок**, найденные по заголовкам первой строки листа; колонки с формулами не затрагиваются. Источник — только значения `_Lists` (`lib/domain/catalog.ts`), стадия новой заявки — всегда «Новый лид».

Заголовки по умолчанию — **предположение** (`lib/integrations/sheets.ts`): `Дата, Имя клиента, Телефон, Источник, Стадия, Этаж, Площадь, м², Вид оплаты, Комментарий`. Обязательны имя, телефон, источник и стадия; остальные пропускаются, если колонки нет. Реальные названия задаются переменной:

```
SHEETS_COLUMNS={"name":"ФИО","phone":"Телефон","source":"Источник","stage":"Стадия","comment":"Примечание"}
```

Если колонка не найдена, запись не выполняется и в логе/БД остаётся понятная ошибка со списком недостающих заголовков.

## Что проверено, а что нет

Автотесты (279, `npm test`): прайс и формула, телефоны, справочники, дедупликация и гонка захвата лида (на in-memory-замене MongoDB), блокировки публикации/эскалации/записи в таблицу, запись в таблицу (на фейковой сетке), подпись и разбор Meta, клиенты Gemini/OpenAI (с подменой `fetch`), ИИ-бот, Shark Tank с фейковым Telegram, обработчики Telegram-бота (команды, ручной ввод, клик 🦈, дедупликация обновлений), приём WhatsApp и Meta, отчёты и их идемпотентность, входящая очередь и восстановление, пересылка сообщений менеджеру, диагностика таблицы, эскалация, склейка сообщений, а также перенесённые тесты Evolution/humanize/JID. Проверены `tsc`, `next build` и ответы роутов на живом сервере.

**Не проверено на реальных сервисах** (в песочнице нет доступа/ключей): настоящая MongoDB (атомарность `findOneAndUpdate` — гарантия самой БД, тест проверяет корректность фильтров), Telegram, Google Sheets, Meta Graph API, Evolution, Gemini/OpenAI. Первый прогон на боевых ключах нужно сделать вручную по чек-листу выше.

## Допущения — проверьте

* Этаж −2 (подвал): в ТЗ **$20 000/м²** при 50% и $18 000 при 100% — почти в 7 раз дороже магазина на 1 этаже. Оставлено как в ТЗ; если это опечатка, правится одной строкой в `lib/domain/pricing.ts`.
* Этажей 0, 2 и 23+ в прайсе нет — бот цену не называет, менеджеру уходит пометка.
* Instagram Direct → источник «Таргет Instagram» (отдельного значения в `_Lists` нет).
* Ручной ввод менеджером: лид **сразу закрепляется за ним** и в группу не идёт (`MANUAL_LEADS_ASSIGN=pool` — отправлять в общую группу как обычный).
* В WhatsApp номер клиента берётся из чата, телефон не спрашивается; в Instagram спрашивается.
* Таджикские фразы запасных ответов и финального сообщения (`lib/services/sales-bot.ts`) стоит вычитать носителем.
* Версия Graph API (`META_GRAPH_VERSION`) и названия моделей Gemini (`GEMINI_MODEL*`) — значения по умолчанию, сверьте с актуальными.
* Если телефон уже есть среди последних 200 строк листа менеджера, новая строка не добавляется (защита от дублей при сбое).
* Состояние склейки и фоновая обработка живут в памяти одного процесса: запускайте **один инстанс**. При нескольких инстансах захват лидов, отчёты и очередь остаются корректными (всё атомарно в БД), но склейка сообщений одного клиента может разойтись по разным процессам.
* Бесплатный Render может перезапустить сервис в любой момент — именно для этого есть входящая очередь.
* При SIGTERM Next.js завершает процесс без ожидания нашего кода, поэтому надёжность перезапуска обеспечивает входящая очередь, а не «дренаж» при остановке.

## Структура

```
lib/domain/        справочники, прайс, телефоны, время
lib/db/            коллекции и индексы, лиды (захват, блокировки), менеджеры, сессии, события
lib/integrations/  Google Sheets, Meta, LLM (Gemini/OpenAI), почта, HTTP с повторами
lib/services/      бот первой линии, пайплайн лидов (Shark Tank), приём WhatsApp/Meta, отчёты, склейка
lib/telegram/      бот, карточки, шлюз
lib/cron/          задачи и планировщик
lib/evolution.ts, humanize.ts, whatsapp-jid.ts   — перенесены из meditour-crm
app/api/           вебхуки (whatsapp, meta, telegram), cron, health
```
